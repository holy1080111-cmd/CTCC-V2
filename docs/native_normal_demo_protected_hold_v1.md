# Native normal Demo protected holding

This is an engineering implementation, not venue acceptance evidence or a claim
of strategy profitability. Normal entry requires the genuine selected physical
DB0058 profile and its exact installed predicate/trigger bodies. Earlier profiles
refuse this action before Arm; importing the schema specification installs nothing.

`POST /api/demo-automation/native/entry-hold` accepts the original fixed native
entry request plus the exact additional confirmation
`HOLD OKX DEMO POSITION WITH ORIGINAL TP SL`. The operator must also type the
existing Arm and execution phrases. It reuses the original native qualification,
G12 publication, fresh execution recheck, atomic reservation, durable intent and
single-use order transport. It does not enable the legacy scheduler or retry.

After an independently verified full fill and active original protection, the
same-request producer appends the unique durable protected-hold lineage, reopens
it in a separate database session, disarms entry authority, closes the owned
HTTP/SDK/read resources, appends and reopens the cleanup journal, and retires only
the matching in-memory ownership graph. Reservation state stays `uncertain`,
revision 3. The event, intent, tombstones and risk reservation remain durable.
The result is `protected_hold`, with retained risk and no execution/retry authority.

The dashboard presents normal holding separately from the explicit acceptance
round trip at `/native/arm-execute`. That acceptance action still immediately
performs its original controlled close after a protected fill. It must not be
described as normal holding.

`POST /api/demo-automation/native/reconcile` selects the original reservation and
opens a new bounded DATA-only source. An exact still-active original protection
produces a durable open-position readback, closes the new read resources and
retains risk. It never recreates Arm, resubmits an entry or cancels protection.

For a terminal original OCO, the new collector retains the exact algo details,
one child order, original entry order, full entry/exit fills, all-account fill
window, current/archive bill chains, balances, positions, pending orders, algos,
leverage and before/after account identity. The original TP, SL, mark triggers,
side and covered size must still match. Missing fields, partial exits, conflicting
pages, foreign activity, ambiguous children or unresolved chronology refuse
resolution. Funding bill generation time is a cashflow observation and is not
reported as accrual time.

The finite DB0058 original-protective-exit predicate and an independent new-session
raw/SQL readback must both pass before transition to `reconciled_flat`, revision 4.
No owned manual-close intent or old own-close closure proof is fabricated. A
fresh process can verify the durable journal without claiming ownership of the
historical process's sockets. The UI clears its known protected-position latch
only for this exact terminal classification with verified fresh-resource cleanup;
generic successful requests do not unlock another entry.

Remaining acceptance work is explicit: the actual combined DB0058 catalog/profile
adapter, actual PostgreSQL positive journal/proof integration, original OCO venue
semantics and the protective-exit forensic/report-outbox admission require their
own completed checks. The existing own-close forensic adapter is not treated as
evidence for an original protective exit. MFE, MAE and other unobserved values
remain incomplete. No live order or Demo order is executed by the tests here.

The authored isolated PostgreSQL schema test is collection-only until the
explicit TLS integration lane executes the actual combined DB0058 migration.
Synthetic unit/DOM checks validate request binding, refusal ordering, source
facts and UI latches; they do not establish authenticated venue provenance.
