# DB0055 native runtime role provisioning

Run migration and provisioning as a separate deployment step. The current image command runs Alembic and Uvicorn with the same database URL. Migration 0055 requires the direct superuser login that owns the existing objects. The native runtime catalog requires a different, restricted writer login. Run the reviewed migrations with the owner and start the API with a restricted runtime configuration and a Uvicorn-only command. Keep the owner login outside the API container.

The API needs three precreated restricted logins on the same PostgreSQL 17 primary and database. `DATABASE_URL` supplies the writer, `OKX_DEMO_NATIVE_CUSTODY_DATABASE_URL` supplies the custody login, and `OKX_DEMO_NATIVE_FRAME_READER_DATABASE_URL` supplies the raw frame login. Frame and raw reading use the same factory. Use the same host, effective port and database in all three asyncpg URLs. The selector rejects URL query options. Provision the login credentials separately. All roles must be direct logins, without membership, elevated attributes or database or public-schema CREATE rights.

`current55_core_grant_sql(writer=..., custody=..., frame_reader=...)` renders the complete proposed core matrix for review. `provision_current55_core_grants(connection, ...)` uses an already-open, idle asyncpg owner connection and an explicit transaction. It checks the sealed owner catalog and reviewed function identities, checks existing privileges and role flags, issues the fixed grants, then reads back the exact target OIDs, non-owner ACLs and effective public table and sequence rights before commit. It requires a fresh core ACL and refuses an already-granted or drifted installation. Supply this during an exclusive deployment window so that independent owner DDL and role edits cannot race it.

The core plan covers the existing isolated writer test matrix for account revisions, Control, reservations, transition locks, outcomes, reports and leverage configuration. It also grants the writer the current55 partition append RPC and the existing partition read RPC. The raw frame login receives both generations of the frame-read RPC and no direct source-table permissions. The custody login receives only the bounded append and read RPCs and no raw-bundle table permissions. All three can read the migration revision. The lock helpers, stopped append and trigger functions receive no new grant.

Before using the result, open fresh direct connections as each runtime login. Use `verify_actual_issuer_catalog_v2` for the writer and `verify_actual_raw_history_catalog_v1` for the frame login paired with the configured writer factory. Call `RuntimeBundleCustodyRepository.verify_deployment` on the custody factory. Verify actual login and effective role equality, distinct role OIDs, the same server and database identity, exact role and ACL facts, installed revision 0055, and the sealed schema digest. Check the writer in read/write and read-only transactions, and verify denial after removing a required grant or adding a prohibited one in a disposable fixture. The existing current55 writer and role tests exercise the first two roles. Add an actual current55 custody-role probe before claiming all-role acceptance. If commit acknowledgement is lost, inspect the actual ACLs with a fresh owner connection before taking any action.

The core receipt deliberately leaves the full application role matrix incomplete. The native source writes B1 capture and B3 observation rows through the writer and reads current observation data. The local mirror locks `demo_automation_state`, `okx_demo_sync_checkpoints`, `okx_demo_order_state`, `okx_demo_position_state` and `okx_demo_algo_order_state`; it also writes the sync checkpoint and `audit_logs`. Verify those precise DML and lock privileges under the actual restricted login in an isolated fixture before extending the matrix. The shared API lifespan may also use paper persistence, legacy Demo mirrors and other enabled services. These paths require a separately verified privilege inventory for the selected deployment settings. A successful local readiness response only proves database and Redis connectivity. Neither this receipt nor the role probes enables execution.
