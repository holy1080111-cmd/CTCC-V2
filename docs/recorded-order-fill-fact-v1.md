# Recorded terminal order and fill-row quantity fact (v1)

`app.trade_evidence.recorded_order_fill_fact.verify_submission_recorded_order_fill_fact` is a pure offline verifier. It accepts the original V5 B1 account journal readback tuple and its five exact pins, plus the original reservation request, submission intent, captured submission, and stored initial outcome JSON/hash. It makes no exchange or database request. It never changes a reservation, sends an order, or grants execution authority.

The verifier first calls the public `verify_history_query_chain` API. That replay checks the B1 event head and chronology, raw body/page/receipt joins, exact account UID and plan, and the packet's required terminal page for every requested V5 stream. It also checks the bounded documented fills/bills query windows. The verifier then calls the public `verify_demo_account_packet`, `prepare_submission`, and `verify_submission_report` APIs. It requires an acknowledged numeric `ordId` and reconstructs the exact stored initial outcome document before reading source rows.

An uncertain or rejected submission outcome has no acknowledged `ordId` in the existing report contract and cannot use this verifier. Searching by `clOrdId` would be ambiguous after terminal reuse. This contract does not solve uncertain-outcome closure.

The only positive assertion is about rows present in that original, verified capture: an exact SWAP order-history row with the acknowledged `ordId`, matching `clOrdId`, instrument, side, position side, isolated mode, FOK type, size and limit price, a terminal filled or canceled state, and a sum of distinct recorded fill rows' `fillSz` equal to the order's recorded `accFillSz`. Each recorded fill must also respect the order's limit price: at or below it for a buy, at or above it for a sell. Overlap by `ordId` or `billId` must have identical canonical source rows; conflicting rows, missing rows, contradictory FOK quantity, timestamps outside the checked sequence, or a second product scope fail closed. A matching `ordId` in `orders_pending`, including a different product, also blocks the fact because this capture cannot resolve that cross-stream state conflict. The receipt preserves the original request/page/row positions and raw event sequences with hashes. It hashes the `ordId` and account scope instead of publishing those identifiers.

The receipt deliberately says `recorded_fill_quantity_matches_acc_fill`. It does **not** prove that every fill ever produced by OKX was retained or returned. The V5 order-history query's retention and late-arrival finality are not verified; the B1 chain is a recorded query, not an authenticated exchange attestation. A future fill, a historical gap, a missed liability, or a later account change remains possible. The receipt fixes `reservation_releasable`, `account_complete`, `source_authenticity_verified`, `execution_authority`, and `order_retry_authority` to `false`, with `admission=DENY`. There is no caller in the ledger, trading routes, or Arm path.

Unit tests exercise a real synthetic V5 B1 journal, including filled and canceled-zero-fill rows, recent/archive overlap, missing order and fill, order/fill mismatches, conflicting duplicate IDs, pending/history conflict, adverse buy/sell fill prices, UID/head pins, and source timestamps. Exact canonical-row comparison on overlapping orders is defense in depth; the V5 JSON parser already rejects JSON numeric scalars, so an integer-versus-boolean equality counterexample cannot occur in a verified V5 packet. The composed receipt test stubs the existing `prepare_submission` and `verify_submission_report` seam so it verifies composition and exact outcome reconstruction, not a real end-to-end V2/V3 submission-lineage replay. Existing real submission fixtures are dated 2024 while the B1 V5 capture fixture is dated 2026; a joint positive fixture requires rebuilding those upstream clocks and evidence, not silently weakening the production clock checks. Production must supply real immutable readbacks and stored submission inputs. No native OKX or PostgreSQL acceptance is claimed by these tests.
