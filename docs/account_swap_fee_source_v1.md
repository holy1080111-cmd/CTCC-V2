# Demo USDT-SWAP fee source diagnostic V1

The [current OKX V5 fee guide](https://www.okx.com/docs-v5/en/#trading-account-rest-api-get-fee-rates) requires `instType` and permits either `groupId` or `instFamily`, but not both. This diagnostic requires `instType=SWAP` with the captured `instFamily` because an `instFamily` query is needed to obtain an applicable rate for a market-maker incentive account; an unqualified query can return an organic base rate. The instrument's `groupId` comes from the [account instruments endpoint](https://www.okx.com/docs-v5/en/#trading-account-rest-api-get-instruments), and the rate is selected from the matching `feeGroup` entry. Deprecated top-level `maker`, `taker`, `makerU`, and `takerU` values are retained only in raw bytes. Positive rates represent rebates; negative rates represent commission. `ts` is the fee data return time, not a fill time, accrual time, historical availability time, or proof that an account has a zero-fee exception.

`app/trade_qualification/account_swap_fee_source_v1.py` replays a pinned V7 Demo account packet and a separate, pinned, bounded raw `GET /api/v5/account/trade-fee?instFamily=<captured family>&instType=SWAP` observation. It checks the exact live linear USDT-SWAP instrument, captures the original instrument/family/group mapping, rejects missing or duplicate groups and malformed rates, checks the response's causal clocks and hashes, and produces a versioned receipt. The raw fee body stays in the diagnostic object; the receipt records its hash and avoids account UID and credential values. Readback recomputes the receipt from both original inputs.

This diagnostic **does not perform an authenticated GET** and does not certify that supplied response bytes came from OKX. It cannot prove the account's original registration site. The present registration-evidence hash in the account plan is only an integrity pin, not that proof. The source-authenticity, account-completeness, fee-freshness, zero-fee override, maker execution mode, and execution-authority fields remain false or unverified, with `admission=DENY`. Native signed fee capture must stay behind independently verified account registration-site routing and the existing owned Demo credential/session, TLS, journal, and readback controls; adding a caller-set `trusted_rate` or `registered_site_proven` boolean would not establish that boundary.

The two raw inputs are synthetic in unit tests. The tests do not establish an actual account fee, account region, economic cost policy, or Demo order eligibility.
